# Creator Studios: research and implementation decisions

Researched 2026-10-22. This is a source-backed design record for the Video and Newsletter studios. External capabilities below describe upstream projects; they are not claims that those capabilities already exist in Ruyix. The installed pack READMEs and checks define Ruyix's current boundary.

## Decision

Use Ruyix's existing Studio, workflow, evidence, approval and artifact-version primitives. Make the video edit decision list an inspectable artifact and render it with local FFmpeg/ffprobe. Add reusable feedback collection and preference context across studios. Keep transcription, advanced motion design and professional-editor interchange as explicit adapters rather than making a large editor or GPU stack mandatory.

Research included the skills.sh directory, primary repositories, actual skill files, licenses and the local Pica/DramaCut implementations. No external skill was installed globally; upstream executable scripts were not run. Skills are useful sources of contracts and review practices, not proof that a product works end to end.

## Local architecture reused as evidence

Ruyix's [Studio design](../design/studio.md) already specifies studios as views and references over workflows, runs and artifacts, with versioned collections. The second and third studios should exercise that contract rather than create parallel stores for copies of the same run.

The sibling `pica/core/plugins/video` already contains a complete short-drama pipeline. Particularly useful reference points are `lib/media.js` (cancellable subprocesses and probing), `lib/plan.js` (range and sentence-boundary validation), `lib/workflow.js` (plan review, apply, voice reuse, render versions) and `lib/revise.js` (human revision). `dramacut/src/dramacut` contains the earlier Python separation of ingest, ASR, shots, plan, captions and render. These are local, product-specific sources rather than newly audited third-party dependencies.

Reuse the concepts and small applicable primitives. Do not import short-drama assumptions such as episode numbering, cliffhanger endings, a mandatory vertical aspect, narration, or platform de-duplication into the general Video Studio. Keep renderer output versions linked to their exact edit plan and supplied source files.

## Product contracts

### Video

1. **Intake and preflight:** identify local uploaded media; probe actual duration, stream presence, frame rate, dimensions and rotation. Reject empty, corrupt, unsupported and out-of-bounds inputs with actionable errors. Do not overwrite the original.
2. **Inspectable plan:** retain a versioned edit list with source identifiers, source ranges, clip identity, requested output format and the reason for each selection. Use one declared timebase; preserve timing precision through render. Agent instructions must match the renderer's implemented schema.
3. **Review and revise:** allow people to inspect source and output, change the plan and ask for a revision. Revalidate every edited plan. Preserve the reviewed plan and prior outputs when rerunning. Regenerate only derived assets whose inputs changed when caching is available.
4. **Render lifecycle:** run with an argument vector, bounded logs, timeout/cancellation and visible failures. Write into the run's artifact area; a partial file cannot be advertised as a completed export.
5. **Output checks:** verify nonzero size, decodable video/audio as applicable, dimensions, duration tolerance and basic A/V continuity. Short synthetic clips should cover no-audio media, mixed aspect/rotation, trim bounds and cancellation. Real-device and real-footage testing is still required for product release.
6. **Export honesty:** distinguish source preview, edit plan, rendered preview and final MP4. A technical pass is not a guarantee of good story pacing, accurate transcript or human-reviewed audio.

### Newsletter

The desired workflow is brief → source evidence → editorial outline → draft → source/claim audit → user review → revised edition/export. Research and writing should be separately inspectable, and a rejected factual assertion must return to the appropriate stage rather than simply making prose more persuasive.

The newsletter implementation also consulted [GPT Researcher](https://github.com/assafelovic/gpt-researcher) for separating source gathering from synthesis, and listmonk's [content/template separation](https://listmonk.app/docs/templating/) and [HTML preview API](https://listmonk.app/docs/apis/templates/). These are architectural references; their code, agent backend and delivery services are not bundled.

Each issue should retain audience, topic, date window, source URLs, relevant dates and evidence for factual claims. Prefer original announcements, documentation and datasets, distinguish reporting from inference, and expose insufficient evidence instead of filling gaps. Explicitly retained drafts and source artifacts let a user rate either research selection or the final writing without confusing the two.

Newsletter Studio should organize issue ideas, editorial profiles, active runs, source/draft artifacts and finished editions. Exporting an edition and sending a newsletter are separate capabilities. A studio that produces an edition must not imply that subscribers have received it.

### Shared feedback and continuous improvement

The first learning layer should be retrieval and explicit preference conditioning, not model-weight training:

- Store the user's score, optional dimensions/tags and written feedback against a concrete run, workflow, stage and artifact/version. Include enough context to know which output the user actually rated; a low research score is not automatically a dislike of the writing style.
- Capture only deliberate user feedback. Completion, absence of complaints, an agent's own review score or a default option is not positive preference evidence.
- Scope examples to the studio and, where known, the editorial/video profile. Preserve contradictory or one-off feedback rather than immediately rewriting global defaults.
- Supply bounded, attributable positive and negative examples to the next relevant planning/writing task. Explain that these are prior preferences; new explicit instructions take precedence. An append-only history plus deletion/retraction provides a path to correct mistaken signals.
- Tie technical quality gates to verifiable defects. User preference can choose pace, tone or density; it cannot establish source truth, legal media rights or a valid media file.
- Measure improvement using subsequent user ratings and accepted revisions. Do not claim a measurable quality gain before collecting comparable evidence. No unattended publication, cross-user learning or automatic model fine-tuning is implied.

## Adopted in this change

The [Video pack](../../packs/video/README.md) implements a native Studio over projects and deliverables, with intake, source inspection, edit plan, timeline review, playable preview, preview review, full export and final review. The independently written [editing skill](../../packs/video/skills/video-editing/SKILL.md) applies the inspected skills' stable-ID, shared-clock, preserved-revision and preview/QA patterns. No upstream editor runtime or skill implementation is bundled.

Video uses local FFmpeg/ffprobe, a versioned JSON EDL and source hashes. Supported operations are trim, reorder, add/remove, speed 0.5–2×, gain 0–2, contain/cover, landscape/portrait/square output, and supplied soft captions. The same rounded output-frame clock determines the timeline, captions and manifest. Preview has a 640-pixel maximum long edge; export is H.264/AAC, at most 1920×1080 pixels. The source and output size/duration/container limits are explicit in the pack README. Source playback uses a registered source ID, subprocesses use generated argument arrays with restricted local input protocols, and render cancellation/timeouts clean up incomplete outputs. Source hashes are checked around rendering, output is probed and fully decoded, and each reviewed render has a manifest and immutable evidence. Approval is bound to the current plan/source/render version; saving while approving or approving stale media is rejected.

Video checks include real native rendering of audible and silent sources, different aspect ratios and frame rates, cut-boundary pixels, decoded audio, exact decoded frame counts, caption streams, preview dimensions and checksums, along with malformed paths/EDLs, subprocess cancellation/timeouts, stale approvals and save concurrency. The separate `packs/video/engine-check.mjs` also passed the real Studio → Workbench engine → timeline save → three version-bound approvals → FFmpeg preview/export → ready-deliverable path, including HTTP Range responses for source media and immutable MP4 evidence, VTT content type and manifest/evidence hashes. The agent pool is a fixture; manual assembly makes no model call. Those fixtures establish a working supported edit/export path, not long-footage stability or playback on every device. Automatic transcription, advanced tracks/transitions, motion templates, TTS, GPU queues and OTIO/NLE export remain deferred. Previous user feedback conditions agent-assisted planning through the common prompt; deterministic manual assembly does not silently change its settings from past ratings.

The [Newsletter pack](../../packs/newsletter/README.md) implements research, outline, draft, independent evidence audit, human review and deterministic Markdown/plain-text/HTML export. Sources retain canonical URLs, publisher/date, captured excerpts and hashes; the normalized research manifest is pinned in the run so subsequent writing cannot replace sources or change both evidence and its hash. Factual prose uses source IDs. Audit coverage must match every substantive prose block; headings alone cannot satisfy it. Unsupported support gets at most two automatic repair attempts and then fails the run rather than marking an edition ready. Edits trigger re-audit; approval pins the edition inputs, and the export manifest records the final bytes' hashes. Generated HTML preview bytes are checked against the current edition before and after review and again at export, so missing/edited previews require regeneration and another review. Source titles are escaped in Markdown and HTML, while plain-text sources are rendered separately. This applies the research/authoring separation above to the existing Ruyix agents. A manually curated source desk is available; saved sources do not silently become issue inputs. Retrieval metadata is supplied by the research agent, and semantic source support still requires reviewer judgment. Deterministic checks, including real engine/Studio success and failure paths, have not demonstrated a live provider research run or email-client compatibility.

The shared Studio implementation stores explicit 1–5 scores and comments against a run/step/result revision, rejects stale and cross-studio submissions, replaces the active score for the same run/target across revisions while retaining version-bound history and supports retraction. The final-result target is separate from a real workflow step named `final`. Structured choices count once per project and scope, need two project confirmations and sufficient agreement, and decay with a 90-day half-life. Recent written reviews are bounded examples, not permanent rules or authority for tool use. A new workflow run captures its preference version; later ratings do not rewrite in-flight context. Learning can be paused without deleting the history.

Feedback is scoped by studio, the run's captured account/profile ID and stage. Account-specific choices and examples do not enter another account's defaults or the no-account profile. The engine resolves and captures the account before selecting its preference snapshot; selecting a run in the feedback UI shows that run's profile. Learning pause is studio-wide. This isolates configured editorial personas while leaving a clear default profile for runs without an account.

`core/plugins/studio/feedback-check.mjs` independently exercises the persistence/service path and the real workflow-engine snapshot path without live models: malformed values, pure scores, repeated-project weighting, disagreement, bounded/stage-scoped written feedback, terminal-target identity, stale-result rejection, studio and persona isolation, correction/retraction, restart, pause, legacy SQLite migration, account resolution and immutable start-time prompt context. These checks establish the implemented mechanics, not a measured increase in creative quality.

`core/plugins/studio/file-check.mjs` covers the generic file field through the real engine attachment boundary: multi/single selections, field names, byte-preserving copies, duplicate Unicode filenames, compatibility with image fields, run copies surviving library removal, isolation from another studio's materials, missing/removed files, required attachment fields and the 20-attachment cap. It uses local byte fixtures, not media decoding or a browser picker.

## Deferred capabilities and release evidence

The initial implementation must enumerate its actual supported input types, timeline operations, caption handling and exports in the pack README. Upstream research does not by itself add automatic transcription, diarization, waveform editing, draggable multitrack timelines, GPU rendering, color management, motion templates, OTIO/NLE import/export, remote render queues or automatic newsletter delivery.

A product release needs evidence beyond unit checks: representative long media and memory behavior, Chinese/English typography and speech where supported, interrupted render recovery, playback in target browsers, editable artifacts after review, feedback isolation/retraction, and several human-reviewed complete workflows. These are acceptance criteria; this research report does not certify they have all passed.
